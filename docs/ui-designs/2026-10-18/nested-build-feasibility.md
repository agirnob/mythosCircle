# Guided Build and Library feasibility

Historical read-only source audit, 2026-10-18. Current accepted direction and required backend work are recorded in [BACKEND-HANDOFF.md](BACKEND-HANDOFF.md); the two-section workspace supersedes the initial combined pre-generation planner presentation below. Recheck source locations and current behavior before implementation. This is design evidence, not an implementation commitment. The DM selected nested cards as the primary editor, a synchronized secondary graph, and AI-assisted structural planning before content generation. The DM selected a separate private Library for Generic characters only.

## What Guided Build already supports

The generation contract is a flat roster of places, factions, and figures with explicit relationships, not a nested document. All three accept stable seed `key` values; relations can address an existing committed entity by `target_id`, a sibling draft by `target_key`, or a name by `target_name`. Figures allow partial authored records; places/factions allow descriptions, archetypes, and dials. See `frontend/src/stores/jobs.ts:29`, `:40`, `:50`, `:59` and the canonical allowed field sets at `backend/app/store/direct.py:105`.

A city with places x/y/z, factions a/b/c, and characters l/m/n/o can therefore be represented today as separate keyed rows and explicit typed edges. The pipeline constructs those declared edges itself rather than asking the model to interpret them (`backend/app/pipeline/build_in.py:1665`, `:3835`). Suitable supported semantics include child place `part_of` city, faction `bases_at` place, character `located_in` place, character `bases_at` home, and character `member_of` faction. The actual kind restrictions live at `backend/app/store/commit.py:69`. A city containing a faction in the outline must not silently imply faction membership or control: the UI needs to state which relationship is created.

Names referenced without a corresponding draft or existing entity become mandatory roster entries, with kind inferred from edge constraints (`backend/app/pipeline/build_in.py:1088`). Missing mandatory targets after regeneration fail before the wave commits (`:3828`). This is useful for simple requests but should not replace explicit typed rows for planned city contents.

The current structured place/faction UI has local numeric draft IDs but submits no seed `key`; it filters and submits only `target_name` relations (`frontend/src/views/BuildInView.vue:461`, `:490`). A nested planner can reuse much of the backend contract while replacing that name-based UI adapter.

## Identity and merge constraints the design must expose

- Preserve a stable draft identifier across rename, reordering, and moving a node. Serialize that identity as `key`, with `target_key` for planned targets; use committed ULIDs for existing targets. Names are labels, not safe node identities.
- Existing-name matching is normalized exact matching; two committed matches fail with an ambiguity error, while a single committed match wins ahead of the generated roster (`backend/app/pipeline/build_in.py:1748`). The normalizer strips articles, folds case/whitespace, and removes trailing punctuation (`backend/app/store/direct.py:705`). A display name such as “The Market” can collide with “Market”.
- Places/factions with the same normalized name and kind update an existing world row; duplicates inside a generated batch fold into the first row. Characters always create fresh ULIDs even when names match (`backend/app/pipeline/build_in.py:2665`, `:2710`). Stable draft keys do not override this merge policy. A planner that permits two distinct same-named taverns needs a new backend identity/merge contract, not merely a better picker.
- Build-in's per-entry validator checks nonblank keys but does not establish whole-roster uniqueness; the resolver indexes keys by assignment, so repeated keys overwrite earlier positions (`backend/app/store/direct.py:588`; `backend/app/pipeline/build_in.py:1698`). Require unique draft keys and validated references before generation; missing/self targets and invalid kind pairs already fail in the resolver (`:1738`, `:1783`).
- Declared duplicate relationships collapse first-wins (`backend/app/pipeline/build_in.py:1787`). Prevent conflicting duplicate controls in the planner rather than implying both declarations survive.

## Recommended DESIGN/EXPERIENCE requirements

1. The DM can create a city, attach planned places and factions, and assign named characters to particular places and optional factions without writing one freeform instruction for the whole structure. A textual route remains fully usable with keyboard and assistive technology regardless of whether a graph is selected.
2. Selecting an existing target and creating a new draft are distinct actions. Show kind, location/context, and existing-versus-draft status in target choices. Renaming a draft keeps every relation intact. Removing a parent explains affected relations and offers reassignment; no silent cascade.
3. Before generation, show the intended entities, relationship direction and meaning, named versus additional generated counts, unresolved targets, duplicate-name collisions, and any existing place/faction that the request may update. Reject ambiguity before spending generation work. A per-parent request such as “generate four people for this tavern” needs an allocation adapter or contract addition: current `generate_counts` specifies global counts by kind, not parent assignment (`frontend/src/stores/jobs.ts:64`).
4. Distinguish an editable planning preview from generated candidate approval. Current Guided Build commits wave 1 directly through `commit_subgraph`; notes may trigger a subsequent wave 2 (`backend/app/pipeline/build_in.py:3875`, `:3898`). Cancellation after wave 1 leaves its committed core (`:3891`). Do not promise “nothing changes until I accept the generated preview” or all-or-nothing multiwave cancellation without a staging/commit contract change. Any new pre-generation preview can describe the plan, not guarantee unseen model output.
5. Result reporting must map draft identities to resulting world entities and show created, updated, merged, skipped, and failed items. The existing wave result and merge reports provide partial foundations (`backend/app/pipeline/build_in.py:3884`); an explicit draft-key-to-final-ULID result map is a new requirement. Keep world-state writes inside `backend/app/store/`.

## Generic and a possible Library page

Generic is already a private per-account character library stored as a campaign with `is_generic=True`. It is storage context, excluded from narrative generation; generation uses the selected theme's default seed (`backend/app/store/campaigns.py:215`; `backend/app/pipeline/build_in.py:3512`). Separating its navigation from “Your worlds” and presenting it as “Library” fits existing storage semantics. It must remain private and must not accidentally supply other saved characters as world context.

Current supported content is characters only. Generic build validation permits figures/theme/concept, rejects world-shaping sections, and rejects character relations (`backend/app/store/jobs.py:577`). A Library containing places, factions, reusable connected collections, or world templates would require additional storage, validation, generation-isolation, and transfer semantics; those categories are not already supported by renaming Generic.

The existing move endpoint moves a character out of Generic into an owned canon world, assigns a fresh ULID, and drops source edges (`backend/app/api/campaigns.py:751`; `backend/app/store/commit.py:1751`). This is a move, not a reusable copy. Despite the function docstring saying “same call,” implementation commits the target and then separately deletes the source (`backend/app/store/commit.py:1825`); do not describe it as an atomic cross-world transaction. A keep-in-Library “copy to world” workflow, bulk collections, retaining relationship graphs, or transferring places/factions all require new contracts. The selected initial Library scope is Generic characters only; broader categories and reusable copies remain out of scope.

## Selected direction: AI-assisted structure before generation

The primary surface is a nested-card planner. Its secondary graph renders the same draft nodes and typed relations, with selection synchronized between both views. AI assists by proposing an outline of places, factions, characters, and relationships; it does not generate full character sheets, lore records, or committed world state at this stage. The DM reviews and edits the proposed structure, accepts it into the draft, and separately starts content generation.

### Existing endpoint feasibility

There is no dedicated typed structural-plan job in `JobCreate.kind` or `JOB_KINDS` (`backend/app/api/jobs.py:32`; `backend/app/store/jobs.py:48`). Existing `generate`/Ask stages proposals without committing world entities, but it produces 2–3 complete records of one requested kind, requires an existing committed world entity, and stages edges to committed targets rather than a proposed nested batch (`backend/app/store/jobs.py:538`, `:881`; `backend/app/pipeline/generate.py:35`, `:175`, `:509`). It is not a structural planner and cannot bootstrap an empty city's outline under its current contract.

The existing `text` job is a genuine non-world-writing primitive: it accepts a prompt and returns unvalidated text in `job.result` (`backend/app/pipeline/worker.py:322`, `:342`, `:345`). It could carry a prototype planning prompt, but it has no typed outline schema, identity reconciliation, graph validation, draft version binding, or merge/accept behavior. It must not be presented as an already-supported safe structural planning API. A new typed planning contract and validation layer are required, whether implemented as a new job kind or a validated planning mode using shared queue/provider machinery. Saving a plan/job is permitted; this stage must write no world entities, edges, or revisions.

### Proposed contract and interaction requirements

1. **Closed structural schema.** Input carries the planning instruction, world identity and revision when applicable, an immutable draft snapshot, and its version. Output carries proposed nodes and typed edges, provenance, and its source draft/world versions. Use an explicit allowlist; reject unknown keys, illegal kinds, malformed fields, undeclared target references, duplicate node/edge IDs, self-relations, and conflicting duplicate relationships. Do not pass model output straight into BuildInPayload. Full authored content belongs to the later generation stage.
2. **Identity survives every view.** Keep stable draft node IDs, edge IDs, and a separate layout map keyed by draft IDs. Rename, reorder, graph selection, and layout changes cannot rewrite relationship identity. Proposed new nodes receive collision-free IDs; edits to existing draft nodes explicitly identify their targets. Bind committed entities by ULID. An accepted draft can later serialize stable IDs into seed `key`/`target_key`. No name-based identity inference during proposal application.
3. **One draft, two projections.** Nested cards and graph must share the same node/edge store. Graph geometry is presentation state, not the containment model. Cards need a defined primary containment parent; faction membership, headquarters, control, and cross-links remain separately typed relations. Avoid duplicating a character's underlying record when it appears under a place and a faction. Supply keyboard controls for every structural action and a textual relationship description.
4. **Containment and kinds.** Validate edge kinds using the server registry (`backend/app/api/campaigns.py:187`; `backend/app/store/commit.py:69`). Reject cyclic primary containment and a node becoming its own ancestor; specify whether other hierarchical `part_of` relations share that acyclic constraint. Non-hierarchical cross-links may form cycles. Current kind rules do not establish a general containment-cycle contract; this is new planner validation, not existing behavior. The UI must distinguish physical location, home/headquarters, organizational membership, and control.
5. **Review is draft-only approval.** Display a proposed change set with added/changed/removed nodes and relations. The DM may edit, accept into the draft, or discard it; accepting never starts content generation or changes world canon. Keep the previous draft intact until application succeeds. The separate generation action summarizes planned creation and existing-place/faction updates. This selected pre-generation review does not change the current direct-commit content-generation behavior described above.
6. **Safe concurrent edits.** Bind each planning request to draft ID/version, world revision, and a request identity. Allow continued draft editing but do not automatically overwrite those edits when a delayed result arrives. Mark obsolete proposals and require an explicit replan or reviewed reconciliation against the latest draft. Recheck source targets and collision rules before applying a proposal and again before generation. Cancellation/discard must prevent late automatic application; retries reuse request identity where appropriate. Preserve user input on planning failures.
7. **Counts and preview honesty.** Show explicit node totals, per-parent allocations, relationship changes, unresolved choices, and possible normalized-name merges before generation. Resolve parent allocations into explicit identified nodes/edges or add a typed allocation contract; global `generate_counts` alone cannot preserve those assignments. Never describe an AI structural preview as a preview of final generated prose or as a committed graph.

These are proposed DESIGN/EXPERIENCE and later API requirements. None has been implemented by this audit. The selected Library scope is Generic characters only.
